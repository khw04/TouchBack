# 오프라인 판정 평가 도구 (C-KH-05 준비)

별도로 기록한 독립 정답과 종료 판정을 run_id/action_id로 연결해 보고서를 만든다. Agent·어댑터·LLM은 정답 파일을 읽지 않는다. 보정 임계값을 조정하거나 live 보정을 활성화하지 않는다. 계측·정답 취득은 현장 담당자가 수행해야 한다.

## 바로 실행할 수 있는 합성 예제

Python 3.12 가상환경·의존성을 설치하고 backend 폴더에서 실행한다.

```powershell
cd C:\TouchBack\backend
..\.venv\Scripts\python.exe -m app.evaluation.cli --references ..\docs\examples\evaluation\mock-references.jsonl --outcomes ..\docs\examples\evaluation\mock-outcomes.jsonl --output ..\data\evaluation-demo.json
```

출력 부모 폴더는 미리 생성한다. 출력 파일은 새 경로여야 하며 기존 결과를 덮어쓰지 않는다. 예제는 전부 **합성된 Mock fixture**이고 실제 Agent 실행 결과·장치 측정이 아니다. 세 실험 중 한 개는 결과 누락, 한 개는 uncertain, 한 개는 정답과 일치하는 합성 성공이다. 분모에 세 실험이 남고 목표 확인 비율은 1/2(정답 +1인 두 실험 중 확인 1개)이다. uncertain 비율은 1/3, 누락 1개이며, 실제 성능 수치로 발표하면 안 된다.

도구가 정상적으로 보고서를 생성하면 종료 코드 0이다. 이는 성능 합격을 뜻하지 않는다. 형식·ID·경로 오류는 2다. 실패·누락·불확실 자체는 평가 대상이므로 보고서에 보존한다.

## 입력 파일 (UTF-8 JSON Lines, 매 줄 LF)

현재 화면 저장본이나 관측 JSONL을 직접 받는 기능은 아니다. 아래 필드로 별도 정답 기록과 실제 종료 판정을 준비한다. 파일당 최대 10000개, 줄당 최대 65536바이트다. 형식 오류·중복 JSON 키·알 수 없는 필드를 조용히 건너뛰지 않는다.

| 파일 | 필드 |
|---|---|
| references | trial_id, run_id, action_id, split=evaluation, source, execution_mode, condition_id, calibration_id, goal, reference_source, before_level, after_level, exclusion_reason(null 또는 이유) |
| outcomes | run_id, action_id, source, execution_mode, goal, status(succeeded/uncertain/stopped/failed), verdict(null 또는 기존 Verdict), latency_ms(null 또는 0 이상 유한 수) |

정확한 JSON은 [정답 예제](examples/evaluation/mock-references.jsonl)와 [결과 예제](examples/evaluation/mock-outcomes.jsonl)를 참고한다. goal은 기존 `{zone_id, direction:increase|decrease, requested_steps:1}` 계약이다. 독립 정답의 `after_level - before_level`을 증가 목표는 +1, 감소 목표는 -1과 비교한다. 예를 들어 감소 목표에서 5→4는 목표 충족, 5→6은 불충족이다. succeeded는 근거 ID가 있는 exact_step/success 판정과 일치해야 한다. backend_stub 성공은 거부한다.

condition_id는 기종·냄비·설치·회로/펌웨어 버전을 식별하는 익명 조건 ID다. 조건 대응표는 실험 자료에 따로 보관한다. calibration_id는 사용한 보정 버전이며 미설정은 unconfigured처럼 명시한다. 같은 그룹 안에서도 조건 변경을 숨기지 않는다.

reference_source는 manual_display/video_display/mock_fixture/unavailable이다. live에 mock_fixture 정답을 붙일 수 없다. unavailable은 전후 단계 모두 null이어야 한다. 표시를 일부 읽지 못한 경우 해당 단계를 null로 기록하면 평가 불가로 남는다. 표시 단계 차이는 열량/소비전력 정답이 아니다. 센서 출력으로 만든 정답을 독립 정답인 것처럼 넣지 않는다.

latency_ms는 실행 기록으로부터 제공한 지연이다. 도구가 시계를 검증하거나 원시 관측에서 지연을 계산하지는 않는다. 실패/중단 결과의 지연도 제공됐다면 포함하며, 누락 지연은 0으로 바꾸지 않는다.

## 집계와 분모

source·execution_mode·condition_id·calibration_id·화구·reference_source별로 별도 그룹을 만든다. Mock, replay, live 또는 서로 다른 보정 결과를 전체 정확도 하나로 합치지 않는다.

| 지표 | 정의 |
|---|---|
| goal_confirmation | 독립 정답이 요청한 방향의 한 단계 변화이며 실제 성공으로 확인한 수 / 독립 정답이 요청한 변화를 충족한 포함 실험 수. 결과 누락도 분모에 남음 |
| false_success_per_included | 독립 정답은 요청한 방향의 한 단계 변화가 아닌데 성공이라고 한 수 / 포함 실험 전체 수 |
| uncertain_per_included | 종료 상태 uncertain 수 / 포함 실험 전체 수. 미수신은 별도 missing_outcomes |
| exact_goal_agreement | exact_step 판정의 goal_satisfied가 독립 목표 충족 여부와 일치한 수 / 독립 정답과 exact_step 판정이 모두 있는 수 |

마지막 지표는 **목표 충족 여부의 일치율**이며 실제 절대 화력 단계의 정확도가 아니다. 분모가 0이면 null이며 0%/100%로 위장하지 않는다. 평가 불가 정답에서 성공을 주장한 수는 unassessable_successes로 남기고 오성공/정상 성공으로 단정하지 않는다.

각 그룹에 누락·평가 불가·제외·정답의 목표 충족·성공 확인·오성공 건수, 상태/판정 수준별 건수, 제공된 지연의 표본 수·최소·최대·평균 및 실험별 판정/근거를 남긴다. 실패/전송 누락을 자동 제외하지 않는다. 제외는 exclusion_reason을 입력했을 때만 하며 전체 행과 제외 사유는 보존한다.

trial_id 또는 run/action 중복, 결과 중복, 정답에 없는 결과, 출처/모드/목표 불일치와 development split은 오류로 거부한다. 잘못 연결된 데이터를 유리하게 집계하지 않는다.

## 한계와 다음 작업

합성 자료로 집계·오염 방지·실제 CLI 실행·출력 보존만 검증했다. 도구가 입력한 정답의 독립성이나 실제 측정을 증명하지 않으므로 physical_validation_performed=false를 기록한다. 실측 자료 수집은 임민혁/차우진, 실측 보정과 시간 매핑 검증은 권희원, 실행/사용량 기록은 윤도훈, 시연 증거 취합은 김민찬의 기존 작업으로 남는다. 실제 환경의 데이터와 측정 조건을 별도로 검토해야 한다.
