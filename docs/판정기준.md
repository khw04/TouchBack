# 검증 수준과 첫 Demo 내부 완료 기준

## 목표와 확인된 사실을 분리

Goal은 zone_id, direction=increase, requested_steps=1을 갖는다.
Verdict는 status(success/mismatch/uncertain), verification_level(none/output_change/exact_step),
goal_satisfied(true/false/null), reason_codes, evidence_ids를 갖는다.
null은 목표 충족 여부 미확인이다. output_change는 추가 사실이며 정확한 단계 성공을 대신하지 않는다.

| 관측 근거 | 판정 | 사용자 안내 |
|---|---|---|
| 보정된 증가 변화만 확인, 단계 구분 불가 | uncertain / output_change / null | 출력 증가를 확인했습니다. 정확히 한 단계인지는 확인하지 못했습니다. |
| 유효한 단계 보정으로 +1 확인 | success / exact_step / true | 화력이 한 단계 올라갔습니다. |
| 유효한 기준에서 +2 등 목표 불일치 확인 | mismatch / exact_step / false | 목표와 다른 변화가 확인되었습니다. 다음 안내를 확인해 주세요. |
| 유효한 시간창에서 변화 없음 | mismatch / none / false | 출력 변화가 확인되지 않았습니다. 입력 미인식 여부를 확인하겠습니다. |
| 센서/시간/보정 누락 또는 판별 불가 | uncertain / none / null | 결과를 확인할 수 없습니다. 추가 조작을 멈춰 주세요. |

비프음 단독으로 성공을 반환하지 않는다. 변화 없음 판정도 관측 시간창과 센서가 해당 변화를 포착할 수 있다는 보정 근거가 필요하다.
LLM은 표현을 바꾸더라도 판정 수준과 확인 범위를 높이지 않는다.

## 두 가지 내부 완료 경로

1. 소프트웨어 P0: 모의 exact_step 정상, 미인식 후보→교정→재검증, 센서 오류→중단을 실제 코드로 재현한다. Agent에 정답을 넣지 않는다.
2. 실측 P0: 보정된 output_change 확인, 유효한 변화 없음 후보 처리, 오류에서 불확실 안내를 재현한다. exact_step은 분리된 실측으로 입증할 때만 추가한다.

실측 P0가 output_change 수준이면 제품의 한 단계 목표를 완전히 검증했다고 발표하지 않는다.
exact_step을 못 얻어도 결과의 한계를 설명하는 실제 Agent Demo는 준비할 수 있다. 대회가 이 축소 범위를 인정할지는 주최측 확인이 필요하다.

## 실측 비교와 기준값

임민혁/차우진이 개발용 측정으로 기종·냄비·위치별 특징과 관측 시간창을 확인한다.
권희원이 그 데이터로 보정 파일을 만들고 임계값/방법/조건/버전을 기록한다.
평가용 반복 측정은 개발용 자료와 분리한다. 평가 샘플로 임계값을 다시 맞추면 새 평가를 수행한다.
adc_count의 큰 증가가 언제나 화력 증가라는 가정을 넣지 않는다. 유효한 보정이 없으면 uncertain이다.
수치 임계값은 현재 정하지 않는다. 목업에는 명시적 mock 보정을 쓰며 실측 보정과 교환하지 않는다.

위 기준은 팀의 첫 구현 확인용이다. 대회 합격 기준이나 원안 전체 완료 조건이 아니다. 원안의 본선 목표는 [본선원안목표](본선원안목표.md)에서 추적한다.
