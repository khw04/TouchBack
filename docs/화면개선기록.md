# 화면 개선 기록

## 1회차 · 안내 중심 화면 (2026-10-10)

공식 수상 사례의 설계 특징을 TouchBack의 목적과 비교했다. 수상 이력은 디자인 참고 근거이며 TouchBack의 성능 증거가 아니다.

| 사례 | 확인한 특징 | TouchBack에 적용한 점 |
|---|---|---|
| [Thermomix TM7 & Cookidoo, UX Design Awards 2025](https://ux-design-awards.com/winners/2025-2-thermomix-tm7-cookidoo) | 조리 과정을 명확한 안내와 시각적 가이드로 따라가게 함 | 실행 상태 아래에 ‘지금 할 일’과 현재 단계·다음 행동을 먼저 표시 |
| [삼성 접근성 가전, iF Design Award 2026](https://ifdesign.com/en/winner-ranking/project/accessibility-design-for-home-appliances/757486) | Easy mode의 큰 글씨와 단순한 화면 구성 | 큰 글씨 전환 버튼과 더 강조된 현재 안내 |
| [Mi Smart Kitchen UI System, iF Design Award](https://ifdesign.com/en/winner-ranking/project/mi-smart-kitchen-ui-system/567387) | 시각 UI와 음성·소리 피드백을 함께 설계 | 문자 안내를 유지하면서 자동 음성 켜기/끄기와 재청취 제공 |

[Google Lookout 설계 사례](https://design.google/library/google-lookout-design-accessibility)는 앱 음성과 화면 낭독기 음성이 겹칠 수 있음을 설명한다. 이를 고려해 자동 읽기를 끌 수 있게 했다. 사용자가 꺼도 새 안내의 텍스트와 재청취 버튼은 유지된다.

이번 변경은 UI fixture에서도 확인할 수 있다. 실제 저시력·시각장애인 사용자 평가, 화면 낭독기 조합별 검사, 실제 Agent 연결은 아직 수행하지 않았다. 다음 회차에는 그 결과나 팀의 통합 API를 근거로 우선순위를 다시 정한다.

## 2회차 · 읽기 쉬운 실행 기록 (PR #10 갱신)

[Apple Design Awards 2025의 Speechify](https://developer.apple.com/design/awards/2025/)는 낮은 인지 부담과 화면 낭독기 지원을 강조하고, [2026 수상작 Guitar Wiz](https://developer.apple.com/design/awards/)는 VoiceOver와 색상 외 구분을 지원한다. TouchBack의 기존 기록은 영어 이벤트 종류, 메시지, 기술 ID가 한 줄에 이어져 읽기 어려웠다.

이번 회차에서는 이벤트 종류와 불확실 판정을 한국어로 표시하고, 메시지·시간을 먼저 보여주며 ID와 근거는 키보드로 펼칠 수 있는 영역에 둔다. 상태 조회에서 이미 보인 이벤트의 DOM을 유지해 펼친 근거와 키보드 초점이 사라지지 않도록 한다. 이는 수상작의 기능을 복제한 것이 아니라 우리 시연의 판단 경로를 더 읽기 쉽게 바꾸는 적용이다.

## 3회차 · 연결 상태와 오래된 결과 구분 (PR #10 갱신)

[Apple Design Awards 2025의 Watch Duty](https://developer.apple.com/design/awards/2025/)는 계속 변하는 정보를 명확하고 신뢰성 있게 전달한 점을 인정받았다. [W3C 상태 메시지 지침](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)은 시각 없이도 중요한 상태 변화를 알 수 있어야 한다고 설명한다.

TouchBack은 서버 연결 상태와 마지막으로 상태를 확인한 시각을 분리해 표시한다. 네트워크 단절과 API 응답 형식 오류도 구분한다. 조회 실패 시 마지막 화면을 현재 상태로 오해하지 않도록 표시하고, 조작 완료·취소 요청의 결과가 불확실할 때는 재제출 버튼을 비활성화한다. ‘상태 다시 확인’이 성공해야 다시 조작 알림을 보낼 수 있다. 실행 생성 요청 자체의 결과가 불명확하면 중복 실행을 막고 서버의 활성 실행 여부를 확인하도록 안내한다. 실제 백엔드 오류 주입 검증은 API 제공 뒤 수행한다.

## 4회차 · 세 시나리오 화면 연습 (PR #10 갱신)

[UX Design Awards 2025의 Thermomix TM7 & Cookidoo 연감](https://ux-design-awards.com/media/pages/events-media/ux-design-awards-yearbook-2025/f1108abc71-1758553537/digital_yearbook_2025.pdf)은 조리 과정을 단계별로 안내하는 화면을 소개한다. [W3C의 상태 메시지 지침](https://www.w3.org/WAI/WCAG21/Understanding/status-messages.html)은 진행·오류 상태의 변화를 보조 기술에도 알리도록 설명한다. 이를 참고해 팀의 평가 시나리오 세 가지를 화면에서 순서대로 연습할 수 있게 했다.

정상 흐름 예시는 가상 관측 뒤 확인 불가로, 미인식 후 복구 예시는 첫 완료 알림 뒤 새로운 action ID의 안내로, 센서 오류 예시는 오류 기록과 확인 불가로 진행한다. 모든 이벤트 출처는 `ui_fixture`, 판정은 `uncertain`, 근거 ID는 빈 목록이다. 시나리오 선택과 현재 연습 이름을 텍스트로 표시하며 실제 API 화면에서는 시나리오 선택을 숨긴다. 이 예시는 시연 동선 검토를 위한 것이며 세 시나리오의 통합 성공 근거로 사용하지 않는다.

## 5회차 · 전달 가능한 실행 기록 (PR #10 갱신)

[Apple Design Awards 2025의 Watch Duty](https://developer.apple.com/design/awards/2025/)는 시시각각 바뀌는 정보를 명확하게 전하는 사례다. TouchBack은 조작 전후의 판정 근거를 팀원이 나중에 다시 확인해야 하므로, 현재 화면의 실행 ID·입력 요청·이벤트·판정·저장 시각을 JSON으로 묶었다. 이 적용은 Watch Duty의 데이터 구조를 따른 것이 아니라 정보의 출처와 시점을 분명히 하려는 설계 판단이다.

파일은 `ui_fixture`·`backend_stub`·`server_response`를 구분하고, 서버 연결이 끊긴 경우 마지막 화면이 오래되었거나 확인되지 않았음을 표시한다. 예상한 이벤트 필드만 저장한다. 인앱 브라우저에서 다운로드 이벤트가 확인되지 않아 동일한 JSON을 화면에도 표시해 선택·복사할 수 있도록 했다. 실제 서버와 일반 브라우저의 파일 다운로드, 실측 증거 대조는 통합 단계에서 확인한다.

## 6회차 · 화구와 목표가 다른 안내 방지 (PR #10 갱신)

[Thermomix TM7 & Cookidoo의 수상 사례](https://ux-design-awards.com/media/pages/events-media/ux-design-awards-yearbook-2025/f1108abc71-1758553537/digital_yearbook_2025.pdf)는 단계별 조리 안내의 일관성을 보여준다. TouchBack 화면 연습은 왼쪽을 선택해도 오른쪽 화구를 안내하는 오류가 있었다. 화구 선택과 입력 문장을 대조해 왼쪽·오른쪽 안내를 맞추고, 두 값이 다르거나 지원하지 않는 목표에는 조작 안내 대신 확인 문구를 표시한다. 이는 화면 fixture의 제한된 예시 해석이며 실제 Agent 목표 해석을 대신하지 않는다.

## 7회차 · 계약 오류와 성공 근거 확인 (PR #10 갱신)

[W3C 오류 식별 지침](https://www.w3.org/WAI/WCAG22/Understanding/error-identification)은 오류의 대상과 내용을 텍스트로 알려야 한다고 설명한다. API 응답의 실행 ID, 상태, 실행 방식, 입력 출처, 안내·이벤트 형식을 확인하고 다르면 `API 응답 형식 오류`를 표시한다. [팀 판정 기준](판정기준.md)에 따라 성공 보고에는 정확 단계 확인, 목표 충족, 관측 근거 ID가 있어야 화면과 음성이 목표 확인으로 안내한다. 이 조건이 빠지면 `성공 근거 부족`을 표시한다. 팀 API의 실제 응답과의 호환 검사는 연결 후 진행한다.

## 8회차 · 실행 ID로 상태 다시 확인 (PR #10 갱신)

[Apple Design Awards 2025 수상작 Watch Duty](https://developer.apple.com/design/awards/2025/)는 변하는 상황을 명확하고 신뢰성 있게 전달하는 사례다. TouchBack에서는 새로고침 뒤 예전 화면을 그대로 현재 상태로 보지 않도록, 서버 실행 ID를 입력해 GET으로 다시 확인하는 경로를 추가했다. 조회는 실행 생성 POST를 보내지 않고 기존 이벤트의 자동 음성을 반복하지 않는다. 임시 검사 서버의 `backend_stub` 응답으로 브라우저 흐름을 확인했고, 실제 팀 서버와의 연동은 대기 중이다.

## 9회차 · 연결 확인 전 이전 판정 가리기 (PR #10 갱신)

[W3C의 상태 메시지 지침](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)은 중요한 상태 변화를 화면 낭독기가 초점을 옮기지 않고도 알 수 있게 하라고 설명한다. 서버 조회 실패 또는 조작 알림·취소 요청 결과가 불확실할 때, 화면 상단의 이전 판정과 조작 안내를 현재 결과처럼 보이지 않게 바꾸고 추가 조작 중단과 상태 재확인을 안내한다. 이전 실행 기록 자체는 남겨 두되 재청취와 새 실행은 상태 확인 전까지 막는다. 정상 조회가 돌아오면 서버 응답으로 다시 표시한다. 실제 팀 서버와 화면 낭독기 조합별 확인은 통합 단계에서 수행한다.
